## RK21, first run (2026-11-24, Claude, Mac Studio)

Reel Kit 1.2.0 was installed on the Mac Studio on Jason's yes (`reelkit install … --yes`). The first try stopped at the transcription model ("couldn't be downloaded"), although each file fetched by hand with the same curl line and matched its pin; the second try set it up whole and Reel Kit's own check passed. The spike used a blank HyperFrames 0.8.139 portrait composition (GSAP from `vendor/`, its CDN line removed, the `CLAUDE.md`/`AGENTS.md` that `init` writes removed), with the profile and settings written by Studio's own `renderProfile` and `workerSettings` (`scratchpad/rk21/harness.mjs`, not kept). No real edit or worker job ran.

- **The render's profile as built refuses HyperFrames.** `check` fails at `listen EPERM 127.0.0.1`: HyperFrames serves the composition to Chrome from a loopback server on a random port (`server.listen(0, "127.0.0.1")`), so no port can be named. With loopback allowed, Chrome dies at `bootstrap_check_in org.chromium.Chromium.MachPortRendezvousServer.<pid>: Permission denied`; then `render` dies at `uv_os_setpriority EPERM` (its lint worker lowers its own priority).
- **Three additions make all of it run** (a copy of the profile, `render-lo.sb`): `(allow network-bind (local ip "localhost:*"))`, `(allow network-inbound (local ip "localhost:*"))` and `(allow network-outbound (remote ip "localhost:*"))` after the `(deny network*)`; `(allow mach-register …)` and `(allow mach-lookup …)` of `global-name-prefix "org.chromium.Chromium.MachPortRendezvousServer."`; and `(allow system-sched)` (`process-info-setcontrol` and `process-info*` with `target self` were each not enough). With them `check` passes (9 layout samples, 5/5 contrast, Chrome on the GPU), `snapshot` writes its frames, and `render -q delivery` makes a 2.000 s 1080×1920 H.264 mp4. Only `~/.cache/hyperframes/chrome` was readable: `fonts/` and `background-removal/` were not needed by this composition (a real card's fonts are still to see).
- **What the additions open.** Inside both profiles: `curl https://example.com` and `curl http://1.1.1.1` fail (000), Python `urllib` fails at name lookup, `open -g https://example.com` and `open -a TextEdit` are refused. But with loopback allowed, the render reaches **every service listening on this Mac's loopback**: `curl http://127.0.0.1:17600/` (Dropbox's local server) answered 404. On the Mac Studio that is Dropbox, Adobe, Claude Code's own local ports, the HyperFrames app, a Python server on 8000/8787 and others. Since the random port can't be named, loopback can't be narrowed to HyperFrames' own server.
- **The worker's sandbox can't run Chrome.** The real worker settings load under `--setting-sources ""` (RK20's first item: the init shows `dontAsk`; a `cd` carries to the next call). The guard refuses HyperFrames commands run from the project root, as built (they run from `public/`). From `public/`, `check` fails at the same loopback listen; `sandbox.network.allowLocalBinding: true` fixes that, and then Chrome dies at the same Mach port registration. `sandbox.network.allowMachLookup` (the only Mach setting Claude Code has) covers lookups only, not registration, and Claude Code says these two settings weaken its isolation. So **HyperFrames' headless Chrome cannot run inside the worker's Claude Code sandbox** as Claude Code 2.1.318 stands.
- **Not yet run** (they wait on the decision below): `denyWrite` and the `Edit()` rules at depth and in mixed case and after a rename, Glob/Grep behind a link, the shell snapshot's environment, a kill mid-step, a card render and a real edit's own-name scan.

**FOR JASON, the decision RK21 was for.** Chrome can't run inside the worker's sandbox, and the render's profile needs loopback, which reaches every local service on the Mac. Choices:
1. *(Recommended)* **Studio runs HyperFrames itself, outside Claude Code's sandbox, under its own profile.** The worker's `check`, `lint`, `snapshot` and card renders go through one Studio-owned wrapper named in `sandbox.excludedCommands` (so Claude Code does not wrap it), and the wrapper runs HyperFrames under `sandbox-exec` with the render profile plus the three additions. Python and ffmpeg stay in Claude Code's sandbox. To be seen first: that `excludedCommands` still applies with `allowUnsandboxedCommands: false`. The cost: a model-written composition can reach local loopback services (no internet, no files outside the project), the same as the render.
2. **Wrap only python/ffmpeg** (the ledger's first fallback): HyperFrames runs with no sandbox at all, guarded by the hook alone.
3. **Accept the hook as a guardrail only** for the whole worker.
Whichever is chosen, the render profile needs the three additions (a code change, test first) before any real render.
